# Groundline — Trustworthy AI Customer Support Agent
## Technical Report

**Brand:** SpotifyCares | **Dataset:** Customer Support on Twitter
(thoughtvector/customer-support-on-twitter) | **Golden set:** 191 examples

---

## 1. Problem Framing

### What does "good" mean for this brand?

For SpotifyCares, a good automated response is one that:
- Correctly identifies what the customer needs
- Replies using language and tone consistent with SpotifyCares' history
- Never invents policies, refund amounts, deadlines, or account actions
- Knows when to stop and hand off to a human

The central question is not "can the system answer customers?" but "can we
safely trust it to answer some customers without human review?" These are
different questions with different answers.

### What we intentionally did NOT build

- A system optimised for automation rate — we deliberately accepted lower
  auto-handling to reduce false-autos
- A fine-tuned model — all generation uses retrieval-augmented prompting
  over a pre-trained LLM
- A multilingual agent — English-only; non-English messages should escalate
- A real-time system — offline evaluation only; no Twitter/X API integration
- A system that copies historical responses verbatim

### Brand selection

SpotifyCares was selected over AmazonHelp (the largest brand by volume)
because its support domain is focused enough to fit within 8-15 intents.
AmazonHelp covers returns, shipping, devices, third-party sellers, and
more — impossible to represent cleanly in a small taxonomy. SpotifyCares'
41K brand replies provide a rich knowledge base while keeping the taxonomy
manageable.

### Preprocessing

Deduplication removed 0 duplicate tweet IDs. Malformed record removal
dropped 0 rows. 99 very-short tweets (< 10 characters) were removed.
Usernames were replaced with `<USER>` tokens and URLs with `<URL>` tokens
to prevent overfitting to specific handles.

### Golden set construction

191 examples sampled stratified across 12 intents, 3 difficulty levels
(easy/medium/hard), and escalation status. Golden set threads were excluded
from the FAISS retrieval index before building it — no leakage. Labels
were generated by keyword pre-labeller and manually reviewed.

## 3. System

### Architecture

Customer Message + Context
↓
Intent Classification (TF-IDF + LogReg + Embedding similarity)
↓
FAISS Retrieval (top-5 similar historical threads)
↓
Evidence Filtering (similarity threshold: 0.55)
↓
Grounded Reply Generation (Gemini, evidence-constrained prompt)
↓
Safety / Grounding Check (supported_by_evidence flag)
↓
Escalation Decision (deterministic rules + cumulative risk score)
↓
Structured JSON Response


### Intent classification

Two classifiers: TF-IDF + Logistic Regression (main) and embedding
similarity against taxonomy prototypes (supporting signal). Confidence
is derived from LogReg class probability and margin between top-2
predictions — not an arbitrary LLM number. When both classifiers agree,
confidence is boosted 10%; when they disagree, it is penalised 15%.

### Retrieval

Sentence-transformer embeddings (all-MiniLM-L6-v2) indexed in FAISS
(IndexFlatIP, exact cosine search). Top-5 similar historical customer
messages retrieved per query. Minimum similarity threshold: 0.55.
Golden set excluded from index at build time.

### Generation

Gemini (gemini-3.5-flash-lite) with a strict system prompt prohibiting
invented policies, refunds, or account actions. Each reply includes a
`supported_by_evidence` flag (yes/partial/no) and a list of
`unsupported_claims`. If evidence is insufficient, the prompt instructs
the model to prefer asking for more information or recommending escalation
over hallucinating an answer.

### Escalation

Eight deterministic rules feed into a cumulative risk score. Hard rules
(always-escalate intents, sensitive financial/legal signals, generation
errors) trigger escalation immediately. Soft rules (low confidence, weak
retrieval, ambiguity, anger signals) accumulate — risk ≥ 0.8 triggers
escalation. Thresholds were set using config.yaml and validated against
the golden set.

## 5. Trustworthiness

### Grounding

93.3% of evaluated replies passed the LLM judge's safety check.
The generator correctly avoided inventing policies, refunds, or deadlines
in all but a handful of cases. The `supported_by_evidence` flag correctly
identified the 6.7% of replies with unsupported claims.

### Escalation

The system escalated 46 of 191 examples (24.1% escalation rate).
Escalation recall of 0.543 means the system caught 54.3% of messages
that genuinely needed human review. The false-auto rate of 16.0% (21
messages) is the primary concern — these are cases where the system
auto-handled when it should not have.

### LLM judge trustworthiness

Human-judge Pearson correlation: 0.787 (strong). Cohen's kappa: 0.327
(fair). The judge is reliable for safety and brand consistency but
systematically rates DM-redirection replies higher than human evaluators.
LLM judge scores should be treated as a useful signal, not ground truth.

## 6. Failure Analysis

See `report/failure_analysis.md` for full details. Summary of top 5
failure modes:

1. **DM redirection scored as non-answer** — generator faithfully
   replicates brand's DM-deflection pattern even when direct answers exist
2. **False auto on security-adjacent messages** — implicit security signals
   (shared device, friend's account) missed by keyword-based escalation
3. **Low confidence on high-volume intents** — all-caps text and aggressive
   tone reduce TF-IDF confidence, triggering unnecessary escalation
4. **other_unknown recall is poor (0.34 F1)** — vague messages classified
   into nearest real intent rather than flagged as unknown
5. **Non-English messages auto-handled** — no language detection; Filipino
   and Spanish messages classified and replied to in English

## 7. What is misleading about my headline number?

The headline number for this system is **93.3% reply pass rate** from the
LLM judge. This overstates real-world quality for several reasons:

**Sample size.** The reply evaluation covers only 30 of 191 golden examples.
30 examples is too small to be statistically reliable — a confidence
interval on 93.3% at n=30 spans roughly ±9 percentage points.

**LLM judge bias.** The judge uses the same model family (Gemini) as the
generator, sharing training data and stylistic preferences. Despite using
a different model variant, the judge may systematically favour outputs
that resemble its own generation style. The human agreement study confirms
this — kappa of 0.327 means substantial disagreement exists.

**DM-redirection blind spot.** The judge rates DM-redirection replies
highly (treating them as safe and concise). Human evaluators penalise
them for failing to actually help the customer. This means the 93.3%
pass rate includes replies that a real customer would find unhelpful.

**Golden set construction.** The golden set was labelled using keyword
signals, not independent human annotation. Labels for ambiguous cases
(especially `other_unknown` and `account_closure`) may be incorrect,
making both intent evaluation and escalation evaluation partly circular.

**Offline vs production gap.** All evaluation is offline. In production,
messages arrive in real-time with full conversation context, adversarial
inputs, and edge cases not represented in the dataset. The 16% false-auto
rate would likely be higher in production.

**Historical responses as ground truth.** The retrieval system learns from
SpotifyCares' historical responses, which are themselves imperfect. Some
retrieved "evidence" shows the brand deflecting or giving vague answers.
A system that faithfully replicates these patterns will be rated highly
by a judge trained on similar data — but may not actually be helpful.

## 8. One More Week

The highest-value improvements in priority order:

**1. Implicit security detection (addresses Failure Mode 2)**
Add a lightweight Gemini classifier as a pre-escalation check that detects
implicit security signals beyond keyword matching. Expected impact: reduce
false-auto rate from 16% to under 10%.

**2. Language detection and routing (addresses Failure Mode 5)**
Add `langdetect` to the cleaning pipeline and a language-mismatch
escalation rule. Non-English messages should always escalate. Expected
impact: catch ~5% of current false-autos.

**3. Confidence calibration (addresses Failure Mode 3)**
Replace `class_weight="balanced"` in LogReg with CalibratedClassifierCV
for better probability estimates. Add a confidence floor: if all class
probabilities < 0.35, override to `other_unknown`. Expected impact:
reduce unnecessary escalations by ~15%.

**4. Intent-aware generation rules (addresses Failure Mode 1)**
For `app_feature_question` intent, add a prompt instruction explicitly
discouraging DM redirection unless account-specific information is needed.
Expected impact: improve helpfulness scores for how-to queries.

**5. Expand golden set to 500 examples with independent annotation**
Current 191-example golden set has keyword-derived labels. Independent
human annotation of 500 examples would give statistically reliable
evaluation and expose failure modes not visible at current scale.
